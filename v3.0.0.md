# Veltix 3.0.0 : Rust-Powered Hot Path

> The first major release built on Rust. The message hot path - parsing, compilation, and buffering -
> now runs compiled code, shipped as one prebuilt wheel per platform, with a transparent pure-Python
> fallback when the native extension is unavailable.

> **Note**: v3.0.0 went through two release candidates (rc1, rc2). The TestPyPI rehearsal caught a
> packaging bug - the sdist declared `License-File: LICENSE` without shipping the file, which would
> have blocked the stable PyPI upload - and the trusted publisher for TestPyPI was configured for the
> first time. The stable release ships everything that rc2 validated.

Veltix 3.0.0 is the biggest internal change since 2.0.0: the framing, parsing, and compilation path is
recompiled in Rust via PyO3 and ships as `veltix._rust` (`cp311-abi3` - one wheel per platform covers
Python 3.11+). When the extension is missing, every call falls back to the pure-Python implementation
transparently.

Zero runtime dependencies. One optional compiled engine. No API change.

## Highlights

### Rust-powered hot path

Message parsing, compilation, and TCP-stream buffering now route through a compiled Rust extension (`veltix._rust`),
exposing the same functions the Python layer already used internally:

```python
from veltix.network import _rust

_rust.rust_enabled()  # -> bool - True when the native extension is active
_rust.engine_name()  # -> "rust" | "python"
```

The Rust code does **wire validation only**: the message-type registry stays in Python, so registering
custom types and routing are completely unchanged. The Rust crates (`veltix-protocol`,
`veltix-message-buffer`, `veltix-bindings`) are pure Rust and fully unit-tested.

### Transparent fallback & runtime engine switch

If `veltix._rust` is not importable, every hot-path call falls back to the pure-Python implementation.
No error, no warning, no change in behavior - just a slower hot path.

```python
# Environment: force the pure-Python fallback for debugging
VELTIX_DISABLE_RUST = 1
python
your_app.py

# Runtime switch (public API)
from veltix import disable_rust, enable_rust

disable_rust()  # all NEW initializations use the pure-Python engine
enable_rust()  # re-enable the compiled engine (when installed)
```

The engine is captured at each (re)initialization - `Server`/`Client` construction, `Server.restart()`,
client reconnection - so already-built components keep the engine they were built with. Toggling the
switch never mutates a running instance.

### Prebuilt wheels for every platform

The build backend moved to **maturin** and the publish pipeline now ships six artifacts: Linux
x86_64 + aarch64 (manylinux 2014), macOS x86_64 + arm64, Windows x86_64, plus an sdist. Because the
extension targets `cp311-abi3`, a single wheel per platform covers Python 3.11 through 3.14 - no more
"build from source if you're not on the CI platform".

`rc` tags publish to TestPyPI, stable tags to PyPI, both through OIDC trusted publishing - no passwords
stored in the repo.

### Deterministic request IDs

The `IDAllocator` is now **pending-safe**: it skips request IDs that still have an active
`send_and_wait()` or `ping()` pending, eliminating wrap-around ID collisions deterministically instead
of relying on probability. The default window grows to the full uint16 range (65535), and an
`IDsExhaustedError` is raised if every ID is busy.

```python
from veltix import IDsExhaustedError  # raised by IDAllocator.allocate() when exhausted
```

### Smoother real-time ticks

The Rust engine removes most of the framing/parse jitter: FPS tick variance drops by half, which
matters most for game servers and real-time dashboards. Combined with lower P99 latency, the hot path
is noticeably steadier under load (full numbers in [Performance](#performance)).

### Cleaner tag updates

`ClientInfo.set_tag()` sets **or overwrites** a tag value in one call - unlike `add_tag()`, which
intentionally refuses to overwrite. This is the intended way to persist mutable state (a score, a
room, a status):

```python
client.set_tag("score", 42)  # emitted as ClientEvent.TAG_UPDATED
```

## What changed

A summary of every user-facing change in v3.0.0, grouped by theme.

### Wire protocol (unchanged)

`pv` stays at 1.0: **v2.0.x peers remain fully wire-compatible**. No protocol migration is needed on
either side.

### Breaking changes

- **Minimum Python version raised to 3.11+** - 3.8, 3.9, and 3.10 are no longer supported.
- **Build backend switched from hatchling to maturin** - matters for anyone building from source:
  the Rust toolchain is now required for source builds (prebuilt wheels ship the compiled engine).
- **Unknown message types are dropped with a `warning`** when received through the wire pipeline,
  instead of triggering buffer resynchronization. Direct `MessageParser.parse()` calls still raise
  `RequestError`.

### Engine control API

- `VELTIX_DISABLE_RUST=1` forces the pure-Python fallback process-wide (hard off - `enable_rust()`
  cannot override it).
- `veltix.enable_rust()` / `veltix.disable_rust()` toggle the engine at runtime for all **new**
  initializations.

### Request IDs & handshake

- `IDAllocator` is pending-safe, default window 65535, raises `IDsExhaustedError` when exhausted.
- The handshake no longer exchanges `id_window` (the client allocator is fixed at 65535). Old peers
  still send/read `meta.id_window` and fall back gracefully; `ServerConfig.id_window` is kept and now
  validated (`1..65535`).
- `ClientAllocator`, the `ClientInfo.id_offset` indirection, `_resolve_global_id()`, and dead
  `_handshake_meta` storage were removed - pending responses now match on raw wire request IDs.

### Tags

- `ClientInfo.set_tag(name, value)` sets or overwrites a tag value.
- New `ClientEvent.TAG_UPDATED` event fires whenever a tag is created or overwritten.

### Removed APIs

- Deprecated `Version` / `COMPATIBILITY` (and `Version.is_compatible()`) - use
  `PROTOCOL_VERSION` / `protocol_is_compatible()` instead.
- Deprecated `Server.get_sender()` / `Client.get_sender()` - use the `server.sender` / `client.sender`
  properties (already the documented pattern since v2.0.0).
- The legacy `veltix-benchmark` console script alias - only `vltxbench` is shipped.

### Postponed

- **`SocketCore.RUST` is postponed to v5.0.0**: the planned Tokio-based socket backend is out of scope
  for v3, which focuses the Rust work on the message hot path (parse/compile/buffering).

## Migration guide

If you're upgrading from v2.0.x, here's what you need to know. **Good news: there are no source-level
API changes and no wire-protocol changes** - the compatibility story is unusually short.

### Python 3.11+ is required

3.8, 3.9, and 3.10 are no longer supported (they are EOL upstream).

### No code changes required

`Request` / `Response` / routing / events / reconnection are all unchanged. v2.0.x clients and servers
talk to v3 peers over the same protocol 1.0.

### Already-deprecated APIs are now removed

```python
# v2.x (deprecated)
from veltix import Version, COMPATIBILITY

server.get_sender().send(request, client)

# v3.0.0
from veltix.internal.compatibility import PROTOCOL_VERSION, protocol_is_compatible

server.send(request, client)
```

### Unknown message types behave differently

Text that names a type the receiving side never registered is now **dropped with a warning** instead
of desynchronizing the buffer. If you relied on observing unknown types through resync, register the
types you expect to receive.

### The engine is automatic (usually invisible)

```python
# v3.0.0 - automatic, nothing to do
from veltix.network import _rust

print(_rust.engine_name())  # -> "rust" on supported platforms

# Force the Python fallback:  VELTIX_DISABLE_RUST=1
# Runtime switch:            veltix.disable_rust() / veltix.enable_rust()
```

## Performance

Rust-vs-fallback numbers measured on Python 3.14.7: 12-core CPU, 30.5 GB RAM, Linux (loopback).
All numbers are 5-run averages, measured in the same time window (see
[PERFORMANCE.md](PERFORMANCE.md) for the full methodology and the socket-backend table).

| Metric                          | Rust engine   | Python fallback | Gain               |
|---------------------------------|---------------|-----------------|--------------------|
| Concurrent stress (100 clients) | 137,995 msg/s | 106,486 msg/s   | **+30%**           |
| Latency average                 | 0.041 ms      | 0.047 ms        | **-13%**           |
| Latency P95                     | 0.048 ms      | 0.061 ms        | **-21%**           |
| Latency P99                     | 0.066 ms      | 0.096 ms        | **-31%**           |
| Jitter                          | 0.019 ms      | 0.014 ms        | ±0 (outlier-bound) |
| Ping throughput                 | 22,582 ping/s | 19,706 ping/s   | **+15%**           |
| Burst send                      | 71,376 msg/s  | 59,408 msg/s    | **+20%**           |
| FPS 64 tick stdev               | 0.175 ms      | 0.343 ms        | **-49%**           |
| Idle server memory              | 60.8 KB       | 60.8 KB         | 0%                 |

FPS *throughput* is tick-limited and unchanged, as expected; jitter (stdev of consecutive ping
deltas) is dominated by rare OS-scheduler outliers and landed within noise in this run. Reproduce
any time with the reworked benchmark CLI:

```bash
pip install "veltix[benchmark]"

vltxbench --engine rust --runs 5 --save a.json
vltxbench --engine python --runs 5 --save b.json
vltxbench --compare a.json b.json          # the table above, regenerated
vltxbench --engine python --socket-core both  # socket-backend comparison
```

The pure-Python `ASYNC` socket backend also holds up under concurrency: ~**2.1x** the stress
throughput of `THREADING` (108,084 vs 51,505 msg/s at 100 clients) - see PERFORMANCE.md.

## Quality

Veltix 3.0 ships with **638 automated tests** covering protocol parsing (with Python/Rust parity
vectors), routing, client/server, reconnection, handshake, IDs, and the engine selection logic.
The suite runs in under 10 seconds via `pytest-xdist`, and CI runs it **twice per Python version**
(3.11-3.14): once with the Rust engine, once with `VELTIX_DISABLE_RUST=1` - both engines must pass
the full suite on every version.

The release-candidate pipeline validated more than code: TestPyPI uploads (fixed the sdist `LICENSE`
packaging bug), OIDC trusted publishing, and the per-platform wheel matrix all shipped as part of the
v3 release process itself, so the stable release is exactly what rc2 validated.

## What next

Veltix will never try to be the fastest framework, the most feature-rich, or a solution for every use
case. That's not the point.

The goal is simpler: make networking something you don't think about. Not a wall you hit, not a layer
of complexity you have to manage : just a tool that works, the way file I/O or threading works in
Python.

## Looking ahead

v3.0.0 proves the hybrid model works: a compiled hot path with a pure-Python fallback, zero
dependencies, and a public API that did not need to change for a major rewrite underneath. Next on
the roadmap is `SocketCore.RUST` (v5.0.0): the same treatment applied to the socket backend itself.
The protocol's reserved flags byte still waits for compression and encryption.

Thank you to everyone who tested the release candidates and helped shape this major update.
